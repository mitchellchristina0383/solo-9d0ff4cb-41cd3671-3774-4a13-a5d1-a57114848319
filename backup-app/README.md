# 备份链管理 · 中间恢复点清退（Flask + SQLite）

一块样例磁盘的**全备 + 按序增量**备份链网页：定长块、内容哈希去重存储；
可按恢复点下载还原镜像；可从链尾上传新导出的同尺寸 RAW 镜像追加增量恢复点；
可清退中间恢复点，把仍需保留的块**并入后继增量**，全程只改指针、不生成临时整盘。

## 一、需求与实现对照

| 需求 | 实现 |
| --- | --- |
| 自带样例盘的全备 + 按序增量，定长块存储 | `app/seed.py`：8 块 × 64B，全备 P0 + 增量 P1~P4；块内容存 `blocks` 表，恢复点经 `backup_blocks` 指针引用，按 SHA-256 哈希去重 |
| 选恢复点下载还原镜像 | `GET /backups/<id>/download`，Flask 流式响应，逐块沿链折叠产出，`Content-Length` 固定为整盘大小，不落临时整盘 |
| 缺省块向前继承 | 还原时把 P0..目标点的指针按序折叠，未显式写入的槽位自然保留前一个恢复点的值 |
| 显式清零块还原为零 | 清零用 `is_zero=1` 的标记块表示，与“未写入（继承）”严格区分；还原产出 `\x00 * block_size`。清零后再被写入可“复活” |
| 清退中间点，把仍需保留的块并入后继，不生成临时整盘 | 两阶段：`prepare` 只把待并入槽位写入暂存表 `staged_blocks`；`publish` 在一个 SQLite 事务内把后继缺的槽位指针并入、删除被清退点。块内容因哈希共享保留，零整盘文件 |
| 其余恢复点编号和还原内容保持原样 | 恢复点 UUID 与显示编号 `seq` 终身不变，清退后 seq 出现缺口但不重排；自测对每个存活点逐字节比对清退前后镜像 |
| 合并准备期间仍可从原链还原 | 准备阶段原链一行不改，仅写暂存表；自测与真实 HTTP 均验证准备期间下载内容不变 |
| 重启后使用最后发布的备份链 | 已发布链即唯一持久链；启动时 `recover_pending_jobs` 把所有未发布的 `ready` 任务标记 `stale`，不自动续作 |
| 两次清退基于同一旧链，先发布生效、另一笔提示重试 | `merge_jobs.based_on_version` 记录基线 `chain_version`；发布用 `BEGIN IMMEDIATE` + 版本 CAS，版本不符返回 409「…旧链已失效，请重试」并标记 `stale`；基于新链重新准备即可成功 |
| 从备份页选定链尾、上传同尺寸 RAW 镜像、追加恢复点 | 备份页「追加恢复点」卡片：链尾下拉（只列当前链尾）+ 文件选择 + 上传/取消。`POST /api/uploads` 登记、`PUT /api/uploads/<id>/data` 以原始字节流上传。`app/upload.py` |
| 镜像逐块读取，不整盘载入内存 | `_Reader` 每次只缓冲一个 `block_size` 的字节；逐块算 SHA-256 与父点同槽比对，比对数据来自 SQL 快照表，内存占用与磁盘大小无关 |
| 与所选恢复点内容相同的块沿用继承 | 与父点同槽内容一致时不写 `backup_blocks` 指针，新点还原时沿链继承 |
| 改成全零的块要显式清零 | 与父点不同且整块全零时写入 `is_zero=1` 的显式清零指针（`ZERO_HASH`），与“未写入=继承”严格区分；下载产出 `\x00 * block_size` |
| 新点完整入链后才可下载 | 恢复点与指针只在整个镜像收齐后的单个 `BEGIN IMMEDIATE` 事务里写入；此前页面上没有该点可下载 |
| 还原内容须与上传逐字节一致 | 入链后 `GET /backups/<id>/download` 与上传镜像逐字节比对（自测与真实 HTTP 均覆盖），并记录整体 SHA-256 |
| 接收和比对期间中间点照常清退 | 接收端每块提交并释放写锁，阻塞等网络时不持有写事务；父点有效内容在登记时用 SQL 窗口函数快照，清退只改指针不改存活点有效内容，故比对不受影响 |
| 提交时所选恢复点仍是链尾即可接上 | `commit_upload` 在写事务内复核 `MAX(seq)` 是否为所选父点；清退造成的指针重排不影响判定 |
| 别的上传抢先接上时提示重选链尾 | 父点不再是链尾时返回 409，任务标 `aborted` 并给出「当前链尾是 Px，请刷新后重新选择链尾再上传」；页面以红色提示要求重选 |
| 长度不符 / 上传中断 / 链尾已变时不留恢复点或新块 | 所有块内容先写 `upload_contents`，指针写 `upload_pointers`；失败/中断/取消/重启都删暂存且不改 `blocks` / `backups`（自测逐项断言） |
| Docker Compose 启动 | `Dockerfile`（python:3.11-slim + Flask 3.1.3）+ `docker-compose.yml`（命名卷 `backup-data` 持久化 `/data/backups.db`） |

### 数据模型（`app/db.py`）

- `meta`：链版本 `chain_version`、块大小、块数
- `backups`：恢复点（UUID、不变 seq、full/inc、标签、时间）
- `blocks`：块内容哈希去重，含一个全局零标记块
- `backup_blocks`：恢复点 → 槽位 → 块指针 + `is_zero`
- `merge_jobs` / `staged_blocks`：清退任务状态机（ready → published / stale）与暂存指针
- `upload_jobs`：链尾上传任务（父点、父点指纹、尺寸、状态 open/committed/aborted、错误、整体 SHA-256）
- `upload_parent_blocks`：登记时父点有效内容的逐槽快照（比对只查此表）
- `upload_contents` / `upload_pointers`：上传中的新块内容与指针暂存区；提交或作废时清空

### 关键并发与一致性

- SQLite 开 WAL、外键、`busy_timeout`；发布事务 `BEGIN IMMEDIATE` 先拿写锁，把并发发布串行化。
- 应用层另限制同时只允许一笔 `ready` 任务，准备即串行；真正的正确性由发布时的版本 CAS 兜底（即使绕过应用层直接插入同基线任务，后发布者仍 409）。
- 每个 HTTP 请求独立连接（`flask.g` + teardown 关闭）；流式下载用专用连接，迭代结束自行关闭。
- 上传：登记时快照父点有效内容；接收时每块一个短写事务，等待客户端数据时不持锁，清退发布可随时插队。提交时在 `BEGIN IMMEDIATE` 内复核“所选父点仍是链尾”与“父点有效内容指纹未变”，任一不符即整体作废；暂存数据仅在提交事务中并入 `blocks`。
- 上传长度：登记时用浏览器给出的文件大小做预检；服务端按磁盘块数与块大小逐块读取，少读、多读、连接中断都返回 400 并作废，且不产生恢复点或新块。

## 二、如何运行

### Docker Compose（交付方式）

```bash
cd backup-app
docker compose up --build
# 浏览器打开 http://localhost:8000
```

数据保存在命名卷 `backup-data`（容器内 `/data/backups.db`），`docker compose down`
后再 `up` 仍使用最后发布的链。

### 本地直跑（无 Docker 时，本仓库自测即采用此方式）

```bash
python3 -m pip install -r requirements.txt
export BACKUP_DB=/tmp/backups.db
python3 -m app.server        # http://127.0.0.1:8000
```

### HTTP 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 管理页面 |
| GET | `/healthz` | 健康检查 + 当前链版本 |
| GET | `/api/chain` | 链与恢复点列表 |
| GET | `/api/jobs` | 清退任务列表 |
| POST | `/api/backups/<id>/prepare` | 准备清退（写暂存区，201） |
| POST | `/api/jobs/<job_id>/publish` | 原子发布（冲突 409） |
| POST | `/api/jobs/<job_id>/abandon` | 放弃待发布任务 |
| GET | `/api/uploads/hint` | 上传预检：整盘字节数、块数、当前链尾 |
| GET | `/api/uploads` | 上传任务列表（含状态与错误） |
| POST | `/api/uploads` | 登记上传（选定链尾 + 文件名/大小/说明，201；尺寸不符 400，非链尾 409） |
| PUT/POST | `/api/uploads/<id>/data` | 原始镜像字节流上传；完整且链尾未变时原子入链（201） |
| POST | `/api/uploads/<id>/abort` | 管理员取消上传，清暂存 |
| GET | `/backups/<id>/download` | 下载还原镜像 |

## 三、实测记录

环境：本机 Python 3.11.2 + Flask 3.1.3（沙箱无 Docker 守护进程，故 Dockerfile/Compose

### 1. 自动化自测 `python3 selftest.py` —— 136 项断言全部通过

- **T1 清零/继承**：P0~P4 五个镜像与独立折叠的真值逐字节一致；验证槽位继承、
  P2/P3 清零持续、P4 清零、清零后被 P4 重写“复活”。
- **T2 清退正确性**：清退 P2 并入 P3 后 5→4 点、seq 为 `[0,1,3,4]`（缺口不重排）、
  UUID 不变；四个存活点镜像与清退前逐字节一致；被清退点 404；重复发布 409；
  数据目录无任何 `.img/.tmp` 整盘文件。T2b 再清退 P1，版本 1→2，存活点仍逐字节一致。
- **T3 交错清退**：同基线（v2）两笔任务，先发布者成功（→v3），后发布者 409 且
  提示「请重试」、任务标 `stale`；基于新链重新准备发布成功。
- **T4 中断重启**：独立库先发布一笔（v1），再准备一笔未发布即重连模拟重启，
  `ready` 任务变 `stale`，服务的仍是最后发布的链（编号 `[0,1,3,4]`、各点镜像不变），
  旧任务发布 409，重新发起后成功（→v2）。
- **T5 HTTP 冒烟**：页面 200、下载 `Content-Length=512` 且哈希与真值一致、
  文件名带编号、不存在点 404、清退全备/末端点 409、工厂重启后无 ready 残留且版本保持。
- **T6 链尾上传**：从 P4 传 512B 镜像（改 1 块、清零 1 块），断言 6 块继承 /
  1 块新写 / 1 块显式清零；新点只显式记录槽位 2、5，清零槽 `is_zero=1`；下载与
  上传逐字节一致、整体 SHA-256 一致；原样再传 8 块全继承、不新增块内容；
  登记尺寸不符被拒且不留任务；流少 1 字节 / 多 1 字节都作废，`blocks`/`backups`
  零新增；选非链尾上传 409。
- **T7 接收期间清退**：可控流让上传停在第三块，此时发布一笔清退 —— 发布成功、
  父点有效内容不变，放行后上传仍提交且下载逐字节一致；反向顺序（先上传后清退）
  内容也不变。场景 C 专门清退父点的直接前驱（父点指针行被并入、行数增加），
  上传仍成功且还原逐字节一致。
- **T8 两份上传争用同一链尾**：A、B 同登记在 P4；A 先提交生效（链版本 +1），
  B 提交返回 409、任务标 `aborted` 且错误含「链尾」、不产生恢复点/新块、暂存清空；
  A 内容不受影响；重选新链尾后 B 重传成功且逐字节一致。
- **T9 重启**：`recover_pending_uploads` 把未完成上传标 `aborted` 并清空暂存，
  链与版本不变。
- **T10 HTTP 层**：`/api/uploads/hint` 尺寸正确；POST 登记 201、PUT 上传 201；
  新点下载 `Content-Length` 正确、与上传逐字节一致、显式清零槽为全零、复活槽为
  写入内容；尺寸不符 400、非链尾 409、流截断 400 且链尾与暂存均无残留；页面含
  上传控件与链尾选择。

### 2. 真实 HTTP 服务（独立进程 + urllib / 裸 socket）

- 下载 P4：512B，槽 3、槽 6 为零，槽 1=E、槽 0=D，符合预期。
- 准备期间再次下载，内容与准备前完全一致；第二笔准备被 409 拦截。
- 交错发布实测：API 任务与直接入库伪造的同基线任务，先发布成功 v2→v3，
  后发布返回 `409 链版本已从 2 变为 3，本笔清退依据的旧链已失效，请重试`。
- 中断重启实测（`restart_test.sh`，SIGKILL 后重启）：未发布任务重启后为 `stale`、
  链仍是最后发布版本、旧任务 409、重新清退成功、P4 镜像与真值一致。
- **上传实测**：真实 HTTP 上传 512B 镜像（6 块继承、1 块新写、1 块清零），
  返回 201；下载新点逐字节一致，清零块为全零。
- **上传期间清退（真实并发）**：A 的 PUT 分块慢发，发到 3/8 块时暂停；主线程
  完成 P2 的准备与发布（v1）；放行后 A 返回 201，新点下载与上传逐字节一致。
- **两份上传争用（真实并发）**：A、B 同登记 P4；A 先完成（v2），B 的 PUT 返回
  `409 所选恢复点 P4 已不是链尾（当前链尾是 P5）…`；B 任务 `aborted`、链尾仍是 A，
  重选链尾后 B 重传成功并逐字节一致。
- **上传中断（裸 socket 提前断开）**：只发 224/512 字节即关闭连接，任务被标
  `aborted`（原因「上传中断：已收到 224 字节」），链仍是 `[0,1,2,3,4]`、版本 0；
  页面取消后状态 `aborted`，再 PUT 返回 409，链仍不变。

## 四、余项与边界

- **未实际构建/运行镜像**：当前沙箱没有 Docker 守护进程，`docker compose up --build`
  仅做了 compose YAML 解析与 Python 编译校验；需在有 Docker 的环境执行确认。
- **上传为整盘流、非断点续传**：失败后需从头重传；暂存内容按任务去重，重复内容不重复写盘，
  但无跨请求的分片偏移记录。可后续加 `Content-Range` 分片续传（提交事务与链尾复核逻辑可复用）。
- **上传事务粒度**：为保证阻塞等待网络数据时不占用 SQLite 写锁，接收端每块提交一次；
  块非常多时会带来较多 WAL 提交开销。可将提交间隔做成可配置（例如每 64 块）并保留
  “等待读流前不持锁”的约束。
- **内存占用**：逐块缓冲 + SQL 折叠，峰值约为“一块 + SQLite 页缓存”；真正的大盘需要
  更大的 `mmap_size`/page cache 调优，但不会出现整盘驻留。
- **Docker 镜像未实测**：本环境无 Docker 守护进程，`docker compose up --build` 未实际执行；
  compose YAML 已解析校验，镜像内容与本地实测运行的 Python/Flask 版本一致（Flask 3.1.3）。
- **开发服务器**：容器用 Flask 内置服务（单映射端口、演示规模）。生产多进程部署需换
  gunicorn/uwsgi，并保证清退发布与上传提交仍走同一 SQLite 库的写事务；已发布链的
  版本 CAS 与“提交时复核链尾”在多 worker 下同样成立。
- **块内容不物理回收**：清退只删指针，哈希共享的块内容保留在 `blocks` 表。如后续要回收
  磁盘，可加“无引用块 GC”，需与发布/提交事务同库处理。
- **单盘模型**：样例为一块磁盘的单条链；多盘/多链需在表上增加 disk 维度。
- **鉴权/审计**：演示未加认证与操作审计；`merge_jobs` 与 `upload_jobs` 保留全部历史
  （含 aborted）可作审计基础。
